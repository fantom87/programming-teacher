## The shopping list

Last lesson every environment started empty. **pip** is how it fills:
`pip install requests` downloads a package from PyPI — the public index
of six hundred thousand of them — into whatever venv is active. But
"just install stuff until it works" doesn't survive contact with a
second machine. Professionals write the list down:

```
# requirements.txt
requests==2.32.5
rich==14.1.0
```

That file is the project's **shopping list**, and `pip install -r
requirements.txt` buys everything on it. Fresh laptop? `venv` +
one command and the project runs. Teammate? Same. The `==` is doing
quiet, important work: it pins the **exact version you tested**, so
next year's requests 3.0 can't silently break your app on someone
else's machine. Lines starting with `#` are comments — professionals
label their lists. (When your env already works, `pip freeze` prints
every installed package *already pinned* — that's where these files
usually come from.)

pip itself needs a real network and a real terminal, so today you'll
do the part that actually requires judgment: **planning** the file.
The starter has a project brief and five candidate packages. Only three
belong. A web *server* framework in a terminal app, or a game engine in
a weather tool, is dead weight that every future install pays for —
picking dependencies is saying no.

### Your goal

Read the brief in the starter, then:

1. Fill `REQUIREMENTS` — a list of exactly three `"name==version"`
   pins, using the brief's tested versions, in the order the brief
   lists them.
2. Write `requirements.txt`: a `#` comment line naming the project,
   then the three pins, one per line.
3. Print the report by looping over `REQUIREMENTS` and splitting each
   pin on `"=="`:

```
requests pinned to 2.32.5
rich pinned to 14.1.0
python-dateutil pinned to 2.9.0
3 packages pinned
```

An AI reviewer checks your *choices* — pick for the brief, not by
coolness.
